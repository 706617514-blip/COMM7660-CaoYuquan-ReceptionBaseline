# Reception Baseline

一个单页静态网页。输入你预期的好评率，得到它在近期 Steam 作品中的百分位。

**打开方式**：双击 `index.html`。无需服务器、无需安装、无需联网。

---

## 它做什么

屏幕上只有一个输入，两个输出。**终点是内容，不是数字。**

```
输入：预期好评率 75 %

输出 ①  第 13.5 百分位 —— 低于市场多数作品
        参照集 159 款中，22 款低于你的预期，137 款更高。
        + 完整分布直方图，标出你的位置

输出 ②  处在同一位置的真实作品（按接近程度排序，每条链到 Steam 商店页）
        BloodDome99              2024-11-15 ·    98 条评论   0.959 (+0.209)
        Saturn                   2024-11-15 ·  1237 条评论   0.768 (+0.018)
        ...

        [显示数量: 5 / 10 / 20]   [评论数下界: 不限 / ≥200 / ≥500 / ≥1000]
```

**两个视图选项只作用于输出 ②，不影响输出 ①。** 这一条有测试保证：改任何一个下拉框，
百分位必须一字不变（见下方验收状态）。

解决的问题有两个。第一，开发者上线前不知道"75% 算好还是差"——Steam 每个商店页都显示
分数，但不显示**分布**。第二，从"我大概会落在哪"到"落在那里的是哪些游戏"没有快捷路径。

**第二条输出正是这个产品属于 media app、而不是仪表盘的理由**：它把用户带到真实的游戏内容
面前，让开发者能直接去看那十款同类作品的商店页、评测和描述。

## 它刻意不做什么

| 不做 | 原因 |
|---|---|
| 不预测你这**这一款**游戏的好评率 | 品类、商业模式、上线时长、评论量合计只解释不到 1% 的差异（伪 R² = 0.007），没有任何一项显著 |
| 不问品类、付费模式、上线时长 | 界面里没有这些输入，**数据文件里也没有这些列**——见下 |
| 不声称因果 | 观测设计无法识别因果效应 |
| 不做用户画像 | 好评率是评论者中的比例，评论者是玩家的自选子集 |

**"数据文件里也没有这些列"是刻意的结构性约束。**
`reference-distribution.json` 只包含 appid、名称、发行日期、评论数、好评率五列。
`genres` 和 `is_free` 被生成脚本显式剔除，并在文件里记录了剔除原因。
这样"日后不小心加上条件筛选"在结构上不可能发生，而不是靠界面自觉。
完整数据集（含全部字段）在 `data/clean/analysis_dataset.csv`，任何人可去核对。

## 文件

| 文件 | 说明 | 可否手改 |
|---|---|---|
| `index.html` | 应用本体（HTML + CSS + JS，无依赖） | 可以 |
| `reference-data.js` | 数据，包成 JS 变量供 `<script>` 直接加载 | **不要**，由脚本生成 |
| `reference-distribution.json` | 同一份数据的纯 JSON 版，便于审计 | **不要**，由脚本生成 |

### 为什么数据用 `<script>` 而不是 `fetch`

页面要能双击直接打开。`fetch` 读本地文件会被 `file://` 的 CORS 规则拦掉，
而 `<script src>` 不受该限制。所以数据以 JS 变量提供，同时另存一份 JSON 供审计。

## 重新生成数据

```bash
python analysis/build_product_data.py
```

该脚本从 `data/clean/analysis_dataset.csv` 读取，重算参照分布，并做三项断言：

1. 源数据集必须含有限制字段（否则说明读错了文件）；
2. 产品数据不得出现白名单以外的字段；
3. 产品数据不得泄漏 `genres`、`is_free` 等会引入条件筛选的列。

任一项不通过就以非零码退出，不会写出半成品数据。

## 百分位定义

把 159 款作品按好评率升序排列，将输入值**线性插值**到排序位置上，再换算为 0–100。

选择插值而不是简单的"低于你的款数 ÷ 总数"，是因为 PRD 要求百分位在输入区间上**严格单调递增**：
输入变大，结果必须变大。简单计数法在数据点之间是平的，插值法不是。

在 1001 个采样点上验证过：无一处下降（见下"验收状态"）。

## 验收状态

对照 `docs/prd.md` 的验收标准逐条核对。可自动化的部分由
`tests/test_product_app.js` 用 Node 实跑验证——**44 项断言全部通过**。

**为什么需要一个 DOM 替身测试**：百分位算法可以单独验，但页面还有一半逻辑在 DOM 接线里
（事件绑定、错误分支、重置、图表绘制）。静态渲染器（如 Quick Look）**不执行 JS**，
从截图看不出这些有没有坏——第一次渲染的截图里结果区就是空的。
所以测试用一个最小 DOM 替身真正跑一遍页面脚本，逐条断言渲染结果。

node tests/test_product_app.js        # 退出码 0 = 全部通过

## 评论数下界为什么不是"中性的筛选"

这是做这个功能时算出来的一件事，值得写下来，因为它推翻了最初的假设：

| 阈值 | 剩余 | 均值 | p25 | 标准差 |
|---|---|---|---|---|
| ≥50（全部） | 159 | 0.823 | 0.755 | 0.124 |
| ≥200 | 76 | 0.846 | 0.771 | 0.100 |
| ≥500 | 47 | **0.864** | 0.809 | 0.084 |
| ≥1000 | 26 | 0.874 | 0.811 | 0.083 |

**过滤到 ≥500 会把参照集均值推高 4.1 个百分点。** 好评率与 log(评论数) 的相关系数是
r = +0.171，原因也说得通：口碑好的作品评论更多。

所以"只列评论多的作品"不是提高精度，而是**换了一个更乐观的比较集合**。如果做成一个
悄悄改答案的输入框，就违背了产品"不条件化"的核心主张。

处理方式：**百分位永远按完整 159 款计算；过滤器只作用于发现列表；并且把偏移量算出来
直接显示在界面上**——把选择效应摆在明面上，而不是藏起来。

模型里 `log_reviews` 的系数是 +0.119（SE 0.163, p = 0.467），不显著。所以评论数不是
**口碑的预测因子**，但它确实**与口碑相关**——这两件事不是一回事，而后者才是过滤会偏移的原因。


## 为什么它算 media app 而不是仪表盘

作业原文把产品形态限定为四种，其中 **media apps** 的判定是：

> "A general chatbot, scraper, or **dashboard** qualifies only when it is the justified media
> product, not merely an assignment aid… A presentation, non-working mockup, advertising trailer
> alone, or **generic dashboard is not a substitute**. An analytics tool is acceptable only when it
> is the justified product for a defined user."

本产品逐条对上：

| 判定标准 | 本产品 |
|---|---|
| 服务 media 的 discovery / engagement 需求 | 帮开发者**发现**同类游戏，并理解其市场口碑 |
| 有明确用户 | 上线前的独立开发者 |
| 不是 generic | 编码了领域特定结论（属性不预测口碑），而非通用图表工具 |
| 不是 assignment aid | 是给开发者用的工具，不是课程作业的辅助品 |
| 终点是内容 | 输出②直接把用户送到 6 款真实作品的商店页 |

**关键区别在最后一行。** 如果只输出百分位，它确实是一个 dashboard。加上"同一位置的真实
作品"之后，任务的终点变成了**游戏内容本身**——这正是作业给 media app 举的例子
（"a film-discovery app"）所做的事。

复核单调性的独立命令（不依赖测试文件）：

```bash
NODE="/Users/f1gment/Library/Application Support/dsh-desktop/harness/.desktop-bin/node"
"$NODE" -e "
globalThis.window = globalThis;   // 数据文件写的是 window.REFERENCE_DATA
const fs = require('fs');
eval(fs.readFileSync('product/reference-data.js','utf8'));
const html  = fs.readFileSync('product/index.html','utf8');
const RATES = REFERENCE_DATA.rates_sorted.slice(), N = RATES.length;
eval(html.match(/function percentileOf\(v\) \{[\s\S]*?\n  \}/)[0]);
let prev = -1, bad = 0;
for (let i = 0; i <= 1000; i++) { const p = percentileOf(i/1000); if (p < prev) bad++; prev = p; }
console.log('monotonic violations:', bad,
            '| 0.70 ->', percentileOf(0.70).toFixed(1),
            '| 0.90 ->', percentileOf(0.90).toFixed(1));
"
```

预期输出：`monotonic violations: 0 | 0.70 -> 13.5 | 0.90 -> 67.3`

**未验证的部分**：真实浏览器中的视觉呈现与真机字体。以上测试跑的是逻辑与 DOM 接线，
不检查像素。视觉需要人工打开确认。

## 数据来源

| 项目 | 值 |
|---|---|
| 数据集 | `data/clean/analysis_dataset.csv` |
| 参照集 | Steam 作品 159 款，2024-10-09 至 2026-10-09 发行，评论数 ≥ 50 |
| 数据截止日 | 2026-10-09 |
| 采集方式 | Steam 公开文档化接口（`search/results`、`appreviews`、`appdetails`），无限流绕过 |
| 完整分析 | `docs/results.md`、`analysis/results/` |

评分口径：好评率 = `total_positive / (total_positive + total_negative)`，评论者中的比例。
