## 1. 意图与原因

Phase 2 的装备系统已经实现，但**玩家看不到自己收集了什么**。装备掉落会直接进
`meta.inventory`，重复件按 30% 退款消失，玩家从头到尾没有一个地方可以「看我的收藏」。

这一批要解决四件事：

1. **让收集可见** —— 一个能打开的背包，把已获得的装备以图形网格展示
2. **把出售权交还玩家** —— 删除自动退款，改为玩家自己决定卖什么
3. **让交互可读** —— 基地六个点位挤成一排、提示文字盖住名字、按键提示不明确
4. **补齐感官反馈** —— 当前游戏完全是静音的

**为什么不是只加一个「背包列表」：** 列表能表达「我有什么」，但表达不了
「我穿在身上的是什么样」。用户明确要的是左栏看到**角色穿上装备的样子**，
右栏是收藏网格。这两件事必须同时在场，否则玩家要在两个界面之间来回切。

**非目标：**

- 不做物品堆叠/合并。用户已明确选择「一件一格」，理由是视觉收藏感。
- 不做装备强化预览的独立界面。升级仍在兵器架内完成。
- 不做 BGM。音乐滑块先落地但不发声（见 §5.5）。
- 不做武器/装备的拖拽换装。点击 + 按钮已经够用，拖拽会引入命中区与误操作问题。

**反目标（这样做就算失败）：**

- 如果背包面板铺满整个画布、挡住战斗，就是白做 —— 用户明确要求约 40%
- 如果面板能被拖出画布外以致无法操作，就是白做
- 如果每件装备在格子里看不出区别（都像同一个方块），就是白做
- 如果音效在有音效和无音效之间听不出差别（音量太小/太短），就是白做

## 3. 方案选择

### 3.1 背包的承载层：DOM 浮层 vs Phaser 场景 vs rexUI

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 独立 Phaser 场景** | 按 Tab 切到 `BagScene` | 独立场景铺满画布，与「浮窗占 40%、可拖动」的需求直接冲突；拖动还要在场景内重做一套 |
| **B. 复用 DOM `#panel` 浮层** ✅ | 新增背包专用 DOM，沿用 `panelOpen` 暂停早退 | `index.html` 要新写一段布局（左栏 70/30 上下分、右栏网格、页签），不能直接复用 `.card` 竖排 |
| **C. Phaser Container 内绘制** | 纯引擎画，风格最统一 | 网格/页签/悬浮提示/拖动/夹边全手搓；文字排版远比 DOM 差；工作量约为 B 的 2–3 倍 |
| **D. 引入 rexUI 插件** | 用 Sizer 自动排版格子 | **已实测评估并否决**，见下 |

**选 B。** 理由：`openPanel` / `refreshPanel` / `EmberfieldUI.toast` 全部可复用；
`Hub.update` 首行 `if (this.panelOpen) return;` 就是现成的全暂停；
拖动夹边是 20 行指针事件；网格用 CSS Grid、页签用按钮、滚动交给浏览器。
装备贴图已经是 `eq-<slot>-<id>` 的 40×60 canvas 纹理，转成 dataURL 即可放进 DOM `<img>`。

**关于 rexUI（实测记录，不凭印象）：**

用户要求「去 GitHub 找需要的包，能装的就装」。我实际下载
[phaser3-rex-plugins 1.80.20](https://github.com/rexrainbow/phaser3-rex-notes)（MIT）
并在本项目真实页面上验证：

| 检查 | 结果 |
|---|---|
| 本项目 Phaser 版本 | 3.80.1 |
| rexUI 最低版本要求 | `Phaser.VERSION` ≥ 3.60 → 通过 |
| 渲染器 | Canvas（`renderer.type === 1`） |
| 仅加 `<script src>` | 全局 `rexuiplugin` 存在，但 `scene.rexUI === undefined` |
| 在 `plugins.scene` 注册后 | `scene.rexUI.add` 可用，能构建控件，控制台无报错 |
| 体积 | 899 KB（min 单文件；整包解压 108 MB，只能挑单文件） |

**结论：能用，但不用。** rexUI 解决的是「格子自动排版」，而本项目背包的主要工作量在
贴图呈现、分类筛选、卖出确认、拖动夹边 —— rexUI 都不覆盖。用户已同意
「先不装，看效果再说」。**如果后续要做更复杂的动态布局，再回来装。**

### 3.2 「每件掉落都进背包」对经济的影响

删除 30% 自动退款后，重复件不再转化为铜币。玩家要靠**主动出售**换钱。
出售价定为 `50% × (基础价 + 已投入升级费)`。

**风险：** 买入是 100%、卖出是 50%，所以反复买卖不能套利。但重复件大量进入背包后，
卖出的总铜币会**多于**旧的 30% 退款，经济会变松。**处理方式**：实现后用
`tests/bot.js` 的胜率阶梯（零强化/半满/全满）验证，不靠感觉调参。允许的漂移范围见 §6。

### 3.3 分页容量与「页 1 刚好装满」

每页 5 列 × 7 行 = **35 格**。全套装备恰好 21 基础 + 14 特殊 = **35 件**。
用户已选定方案 A：**收满全套即第 1 页满格**，任何重复件立刻溢出到第 2 页。
明确接受「第 1 页收藏收满即满」这一后果，不做单价上限、不做自动扩容提示。

### 3.4 退出战斗的结算

「退出战斗」若简单地按战败结算（保留一半铜币），会**变成优势策略**：
打不过就按 ESC 提前退出，收益与打到死相同但耗时更短。

**采用血量折扣：** 保留率 = `50% × (0.5 + 0.5 × 剩余血量比)`，即满血退出拿 50%，
残血（接近 0）退出拿 25%。这样「早退」永远不如「打赢」，也不优于「打输」。

### 3.5 已核实的实现阻塞点（写文档时逐条查代码确认，非推测）

以下八条是**先查代码、再定方案**的结果。它们不是风险，是已经存在的事实，
设计必须按它们改，否则实现到一半会推倒重来。

#### B1. `meta.inventory` 的数据结构装不下重复件

现状（`logic.js:414,430,433,446-448,566`）：

```js
meta.inventory      // string[]  —— 只是 id 列表
meta.inventoryLevels // { [id]: number } —— 一个 id 只能记一个等级
```

`meta.inventoryLevels[id]` 是**按 id 索引的标量**。同一件装备出现两次
（本批核心要求：重复件也进背包、不堆叠、一件一格），两件的等级无法分别记录：
`upgradeEquipment`（`logic.js:536-537`）对背包里的件是 `inventoryLevels[id] += 1`，
只有一个格子，两次升级同一 id 的不同副本会互相覆盖。

**处理：** 库存改为**条目数组** `meta.bag: [{ id, level }, ...]`，每件一个对象，
等级跟着条目走，天然满足「不堆叠、一件一格」。旧字段在迁移时转成 `bag`
（`inventoryLevels` 只有单值，历史重复件本来也只存了一件 —— 迁移按 id 去重，
不凭空造件）。**`equipOwned` / `equipItem` / `unequipSlot` / `buyEquipment` /
`upgradeEquipment` 全部要改成按条目操作。**

#### B2. 重复件退款目前被记了两次

`logic.js:562-564` 的 `rollEquipDrop` 里 `state.meta.coins += refund`，
`logic.js:1286` 的 `killEnemy` 里又 `run.loot.coins += drop.refund`。
同一笔退款进了两处，是现状缺陷。本批删除整条退款路径，它会一并消失，
但删除时必须**两处都删**。

#### B3. 战斗场景没有暂停机制

设计原文假设「`panelOpen` 早退是现成的全暂停」。**核实：只对 Hub 成立。**

- `Hub.update`（`app.js:1530`）首行确实是 `if (this.panelOpen) return;`
- **`RunScene.update`（`app.js:1627-1635`）没有这个早退**，它无条件执行
  `L.step(this.state, input, dt)`，每帧都在推进模拟。

所以「战斗中按 ESC / Tab 暂停」**不能靠复用现有机制**，必须在 `RunScene.update`
里新增等价守卫。**这是本批的新增工作量，原文漏了。**

#### B4. `Tab` 不在输入映射里，且会抢焦点

`createInput` 的 `CODES`（`app.js:858-873`）有 `Escape: 'esc'`，**没有 `Tab`**。
且 `Tab` 默认移动焦点，不 `preventDefault()` 会把焦点移出画布、后续按键全失效。
现有代码只对 `Space` 和 `Shift*` 做了 `preventDefault()`。

**处理：** `CODES` 加 `Tab: 'bag'`，并在 `onDown` 的 `preventDefault` 条件里加 `Tab`。

#### B5. 装备贴图不能直接变成 DOM `<img>`

原文说「贴图是 canvas 纹理，转 dataURL 即可」。**核实：需要中间步骤。**

`equipLayer`（`app.js:250-254`）用 `g.generateTexture(key, 40, 60)` 交给 Phaser
纹理管理器。拿到的 source **是 `HTMLCanvasElement`**（实测可 `drawImage` 到新
canvas 并 `getImageData`），但**不能直接塞进 `<img>.src`**：

```js
const src = scene.textures.get(key).getSourceImage(); // HTMLCanvasElement
const dataUrl = src.toDataURL('image/png');            // 这才有 src
```

**可行，但必须一次性做好并缓存**（35 件各转一次），不能每帧转 —— `toDataURL`
是同步且昂贵的。设计采用「首次开背包时批量转一次，缓存在模块级 Map 里」。

#### B6. 卖价的「已投入升级费」可以算出，但必须复用同一份定价

`upgradeCost(state, key)` 是**强化升级**（攻击/生命/移速）的公式，**不是装备升级的**。
已投入升级费 = 从 Lv1 升到当前等级，逐级累加**装备**升级价，用 `EQUIP_LEVEL` 的规则
（`priceGrowth`、基础件 3 级 / 特殊件 5 级）。**实现必须复用 `upgradeEquipment` 里
同一个定价函数**，不能另写一份 —— 两份公式漂移，玩家卖价就对不上曾经花掉的钱。

#### B7. `refundRatio` 的全部出现位置（删除时一处都不能漏）

| 位置 | 内容 |
|---|---|
| `config.js:416` | `EQUIP_DROP.refundRatio: 0.30` |
| `logic.js:562-564` | `rollEquipDrop` 里算退款并加币 |
| `logic.js:1283` | 掉落对象带 `refund` 字段 |
| `logic.js:1286` | `killEnemy` 里 `run.loot.coins += drop.refund` |
| `app.js:1667` | 掉落提示文案显示「折算 N 铜币」 |
| `tests/test_game_logic.js:1383` | 断言 `refundRatio === 0.30` |
| `analysis/build_report2.py:109` | **报告生成器**：`Math.round(C.EQUIP_DROP.refundRatio*100)` |
| `analysis/build_report2.py:119` | `vals["refund_pct"] = eq["refund"]` |
| `analysis/build_report2.py:303` | 报告正文 `f"refunded at {v['refund_pct']}%"` |

最后一条是**测试**：删掉退款后这条断言必须改写，不能留着假装还成立。

**第 7–9 处（本轮复审补记，原稿漏列）**：报告生成器 `analysis/build_report2.py` 也读 `refundRatio`。
它**不在任何任务的 Files 列表里**，Task 15 只跑游戏内测试套件，所以没有任何任务会碰到它。
失败模式比"崩溃"更隐蔽：`Math.round(undefined*100)` 是 `NaN`，`JSON.stringify` 把 `NaN`
序列化成 **`null`**（键不会消失，所以**不抛 `KeyError`**），脚本继续跑到 :303，
把 **`refunded at None%`** 静默写进 Phase 2 报告。崩溃会被发现，`None%` 会一路进文档。
→ 必须在重新生成 Phase 2 报告之前处理：删掉 :109 的 `refund` 表达式、:119 的赋值、
以及 :303 那句"折算"叙述（产品已改为玩家自行出售）。**已归入 Task 15（收尾）**。

#### B8. 存档迁移：`STATE_VERSION` 5 → 6，且迁移必须排在默认值之前

核实 `logic.js`：`STATE_VERSION = 5`（第 17 行），`migrate()`（1623-1649）
是一串顺序的 `if (s.version === N) { ...; s.version = N+1; }`，
`serialize`/`deserialize`（1651-1655）在版本不匹配时**直接抛异常**
（`存档版本不匹配: N（当前 M）`）。

**所以只加字段是不够的**：

1. 必须**新增一段 `if (s.version === 5) { ... s.version = 6; }`**，
   把 `meta.inventory` + `meta.inventoryLevels` 转成
   `meta.bag: [{ id, level }, ...]`，并补 `meta.bagPages = 1`。
   **按 id 去重**，不凭空造件 —— 旧结构本来就只存得下一件。
2. `STATE_VERSION` 改成 **6**。
3. **`logic.js:1657-1668` 一带的兜底默认值不能替代迁移**：它们在版本校验
   **之后**才跑，而版本不匹配会先抛异常。靠兜底会让老存档直接崩。
4. **`tests/test_game_logic.js:342` 的 v2 夹具必须能一路链到 6**
   （2→3→4→5→6），
   这条测试正是为「老存档不会崩」而存在的，改动后必须仍然成立。
5. **`meta.bagPages` 的归属要定**：它存在 `meta` 里，就会跟着
   `profile.js` 的 `exportCode`/`importCode` 一起走（导出串里带页数）。
   **本设计选「跟着走」**（换设备不该丢已买的页），
   但这条**要 PM 确认**（见 §6 之后的待定问题）。

### 4.2 拖动与夹边

- 拖动把手：标题栏整条。
- `pointerdown` → 记录偏移 → `pointermove` 更新 `left/top` → `pointerup` 结束。
- **夹边规则**：`left ∈ [0, frameW - panelW]`、`top ∈ [0, frameH - panelH]`，
  用 `Math.max/Math.min` 夹住。面板永远无法被拖出画布。
- 位置**不持久化**（每次打开回到默认位置），因为持久化的位置在窗口尺寸变化后
  可能落在界外 —— 那正是夹边要防的情况。

> **实施澄清（2026-11-12，Task 7 落地时定）**：夹边的参照系取 **viewport**
> （`innerWidth/innerHeight`），不是 `#frame` 的盒子。原因：`#frame` 是
> `max-width:980px; aspect-ratio:960/600` 的等比缩放容器，`#bag` 用
> `position:fixed` 是为了让指针位移与面板位移 1:1（放 absolute 里会被缩放，
> 窗口一大一小就明显错位）。用 fixed 就必须按 viewport 夹边，否则两者坐标系不一致。
> **默认位置改为画布右下角内缩 16px**（原写「居中偏左」）：角色就在画面正中，
> 面板一开就糊在脸上，第一眼看到的是「我被挡住了」。实测出生点 `(451,469)`
> 在面板之外，不被遮挡。

> 980px 的画框，留白有限，可接受；若以后要严格限制在画框内，需改成
> absolute + 按缩放比换算指针位移。

### 4.5 整理（排序）

1. 稀有度：特殊（`kind === 'special'`）在前，基础在后
2. 槽位顺序：`head → torso → back → weapon → feet`

### 4.6 出售

- **右键点击格子**触发。
- 弹确认条：「出售 荆棘甲 Lv3 · 收回 **1593** 铜币？[确认][取消]」。

  > **实施改动（2026-11-12，Task 8 落地时定）**：**单件右键改为直接卖出 + toast 提示**，
  > 去掉确认条。理由：用户原话是「右键出售」，逐件弹确认会让"清包"这件高频操作变成
  > 两次点击 × N 次；而误卖的兜底已经有 —— **批量出售**仍走整批确认（显示总件数 + 总价），
  > 且「每 id 至少留一件」保证不会把某个 id 卖光。toast 会写明「卖掉了什么 · 收回多少铜币」，
  > 卖错也看得见。
  > 若 PM 要求恢复确认条，改 `baghud.js` 的 `contextmenu` 分支一处即可，测试需同步调整。
- 确认后：`meta.coins += sellValue(item.id, item.level)`，并从 `meta.bag` 移除该条目。
- **不得出售已穿戴的装备**。若右键的是当前穿戴件，提示「先卸下才能卖」。
  （理由：穿在身上的那份不在库存里，但玩家的直觉是「我看到它了」，
  必须给出明确原因而不是静默失败。）
- **卖出价公式（已核实签名，原文写错）：**

  ```
  sellValue(id, level)
    = floor(0.5 × (C.equipDef(id).price
                   + Σ_{lv = 2 .. level} C.equipPrice(id, lv)))
  ```

  **原文写 `equipPrice(slot, id)` 是错的。** 核实 `logic.js`：
  `equipPrice(id, level)` 是**两个参数**，没有 `slot`；基础价直接用
  `C.equipDef(id).price`。写错了会直接算出 `NaN`。

  「已投入升级费」= 从 Lv1 升到当前等级逐级累加**装备**升级价。

  **直接复用现成函数，不要自己再写循环**：`C.equipPrice(id, lv)`（`config.js:432`）
  就是单级价，`Math.round(def.price * priceGrowth^(lv-1))`；
  而 `logic.js:492` 已有的 `equipUpgradeCost(state, id)` 是「**下一级**的价格」。
  卖价需要的总和写成一个小工具即可：

  ```js
  function equipInvested(id, level) {
    let sum = 0;
    for (let lv = 2; lv <= level; lv++) sum += C.equipPrice(id, lv);
    return sum;
  }
  ```

  **注意 `equipUpgradeCost` 不能直接拿来加总**：它返回的是下一级价，
  而且它的等级取值逻辑读的是 `equipOwned(state, id)` +
  `inventoryLevels[id]`（**按 id 索引的标量**）—— 这正是 §3.5-B1 要去掉的结构。
  改成条目数组后，`equipUpgradeCost` 与 `upgradeEquipment` **两者都要改**，
  改成按「具体那个条目」取等级。**只改存储不改这两个函数，升级会永远只升第一件。**

  另注：`upgradeCost(state, key)`（`logic.js:375-380`）是**角色**强化
  （攻击/生命/移速）的公式，读 `C.UPGRADES[key]`，**与装备无关**，
  原文差点用它。**别用错。**

  **实测数值（本机跑脚本直接算出，供实现者写测试用）：**

  | 件 | 基础价 | 类型 | 上限 | Lv1 | Lv2 | Lv3 | Lv4 | Lv5 |
  |---|---|---|---|---|---|---|---|---|
  | `thornMail` | 700 | special | 5 | 350 | 857 | **1593** | 2660 | 4207 |
  | `longCloak` | 200 | base | 3 | 100 | 245 | 455 | — | — |
  | `windBoots` | 200 | base | 3 | 100 | 245 | 455 | — | — |

  原文示例里的「荆棘甲 Lv3 · 收回 245」是错的 —— **245 是 200 价件在 Lv2 的数**，
  和荆棘甲 Lv3 无关（荆棘甲 Lv3 是 **1593**）。验收测试用 **1593**。
  这张表就是 V8 的断言依据：`floor(0.5×(700 + equipPrice(id,2) + equipPrice(id,3))) = 1593`。

- **买卖往返必然亏损，且亏损的是全部投入的 50%，不是「只亏基础价的 50%」。**
  原文把理由写成「卖价能对上曾经花掉的钱」是**描述错误**：
  50% 的公式对**升级费**也同样打折，所以升过级的件卖掉一定亏一半升级费。
  这是刻意的设计（否则反复买进卖出可以套利），但文档必须把话说准，
  否则实现者可能读成「只按基础价 50% 退款、升级费全额返还」。

### 4.6.1 批量出售（PM 追加，已确认规则）

**设计立场：批量出售是玩家的动作，不是系统自动行为。** 系统仍然一件不落地
把掉落塞进背包（§3.2），批量出售只是给玩家一个一次性清掉冗余的手段 ——
和「收集癖」不冲突。

**入口**：背包标题栏，`[整理]` 旁加 `[批量出售]`。

**交互**：点开后背包进入选择态，每格左上角出现勾选框。工具条给三个快捷勾选：

| 快捷勾选 | 规则 |
|---|---|
| 勾选全部重复件 | 同一 id 拥有 ≥2 件时，保留**等级最高**的一件（等级相同保留第一件），其余全勾上 |
| 勾选全部未穿戴基础件 | `kind === 'base'` 且当前未穿戴 |
| 全选 / 全不选 | 字面意义，**但受下方两条硬约束限制** |

「勾选全部重复件」是本批最有用的一个动作：接住 §3.3 的 plan A ——
集齐 35 件后任何重复件立刻溢到第 2 页，这个按钮一键把它们变成钱。

**硬约束（PM 已确认，两条都要）：**

1. **每件至少保留 1 件。** 即使按了「全选」，同一 id 也会**强制留一件**
   （留等级最高的那件）。防止一次误点清空整套收藏 ——
   玩家要的是收集癖，不是清仓。
2. **不允许出售已穿戴的装备。** 与 §4.6 单件出售完全一致：
   已穿戴的格子勾选框**灰掉**，并给一行说明「穿在身上的先卸下」。
   **不做**「自动先卸下再卖」的便利路径 —— 保持与单件行为一致，
   少一个例外就少一类 bug。

**确认与结算**：

- 确认框显示**总件数与总价**：「出售 12 件 · 共 **4,830** 铜币？[确认][取消]」，
  不逐件询问。
- 一次扣款、一次从 `meta.bag` 移除、一条 toast。**不做逐件动画堆叠**
  （几十件同时飞出去既卡又难看清）。
- 卖出价逐件按 §4.6 的 `sellValue(id, level)` 计算后**求和**，
  不是「按其中一件的价 × 件数」。

**边界情况：**

- 一件都没勾选时，确认按钮**禁用**（不是弹「请先选择」）。
- 全部装备都是「已穿戴 + 每 id 仅 1 件」时，三个快捷勾选都会勾出 0 件，
  此时显示「没有可出售的装备」并说明原因。

**布局（2026-11-12 修订，Task 16）：选择态工具条横跨整个面板。**

初稿把这条工具条放在右栏（`#bag-right`）底部，与分页条共用 24px 槽位。
面板从 620 收到 470（§4.1 的修正）后右栏只剩 267px，而工具条内容需要
334px（零选）/ 362px（选中 2 件）—— `#bag{overflow:hidden}` 直接把
「确认」「取消」切掉，`elementFromPoint` 打在两颗按钮中心都返回 `BODY`，
**鼠标点不到**。1348 条断言全绿也没抓到，因为它们用 `.click()` 而非几何。
（教训记在这里：`.click()` 能证明回调接对了，不能证明玩家够得着。）

修订：工具条移出右栏、作为 `#bag` 的直接子元素横跨面板全宽（可用 454px）。
**面板总高与网格高度都不变** —— 分页条与批量工具条本来互斥（同一 24px 槽位，
从不同时可见），批量态下右栏少一条、面板级多一条，净变化为零。
验收表相应补 **V30**：真浏览器里两点按钮都在面板矩形内、`elementFromPoint`
命中它们自己。

### 4.8 暂停

打开背包 / ESC 菜单时**游戏完全暂停**。

**实现方式（PM 已选定「正确档」）：`this.scene.pause()`，不是在 `update` 首行早退。**

核实：`Hub.update`（`app.js:1530`）有 `if (this.panelOpen) return;`，
但 `RunScene.update`（`app.js:1627`）**没有**任何守卫。**两个场景统一改用
`scene.pause()`**，不再靠 `update` 早退。

**这个选择有三个后果，必须写清而不是假装不存在：**

1. **暂停期间 HUD 不刷新**（血量/铜币/波次停在最后一帧的值）。这在暂停时是
   正确行为 —— 游戏停了数字就不该跳。
2. **DOM 浮层活在 Phaser 之外，照样可点、可拖、可右键卖。** 这正是选它而
   不选早退的理由：早退会把 `run.equipDrops` 的排空（`app.js:1661-1672`）
   一起冻住，导致「在暂停里卖掉一件刚落地的装备」结算顺序未定义。
3. **回调会打进已暂停场景的闭包。** 卖掉/穿脱装备后触发的
   `refreshHeroEquip(this.hero, this.state)` 是在暂停态下执行的。
   装备图层的重绘不依赖 `update` 循环，**所以能生效，但这是要验证的**
   —— 装备系统已有过一次真实缺陷（面板打开时换装看不到变化），
   本批**必须为这条单独写测试**，不能假设没事。

**恢复时机**：关闭背包/菜单时 `scene.resume()`。**必须成对**：
`pause` 之后如果异常退出（比如抛错）而没 `resume`，玩家会卡在死场景里。
用 `try/finally` 或「关闭路径唯一化」保证成对。

### 5.3 基地错落布局

六个点位由一排改为**上下错落**。**先核实再改：`hub.js` 的 `ZONES`

1. `ZONES` 每项加 `z`（错落深度，约 0 / ±34，即约 1/3 屏高的错开量）；
2. `zoneAt` 改为按**屏幕距离**判定，不能只比 `x`。否则上下错开的两个点位

3. 绘制端（`app.js:1340` 一带，目前所有点位画在同一个

   `toScreen(x, z, 0)` 取各自的屏幕 y，并按 `sc` 缩放，否则「错落」在画面上
   看不出来 —— 数据改了、画面没改，等于没做。

| id | name | x | z | 位置 |
|---|---|---|---|---|
| field | 田地 | 100 | 88 | 下 |
| anvil | 铁匠铺 | 265 | 122 | 上 |
| forgewear | 兵器架 | 415 | 88 | 下 |
| shop | 药水铺 | 565 | 122 | 上 |
| altar | 技能祭坛 | 720 | 88 | 下 |
| gate | 远征之门 | 880 | 105 | 中 |

> **z 值不是从 0 起算的（2026-11-12 修订）**：初稿写 `0 / 34 / 0 / 34 / 0 / 17`，
> 但绘制端是 `sy = GROUND_Y - z*Z_TO_Y`（`GROUND_Y = 515`，画布高 600）。
> 把三个点位放到 `z = 0` 等于把它们的底边压到 `y = 515`，整排往下掉约 **107px**，
> 地面光池与设施美术会挤到画布底边、压住底部 HUD。改成围绕原来的构图中心
> `HUB_D/2 = 105` 上下各偏 17：下排 `z = 88`（`y ≈ 425`）、上排 `z = 122`（`y ≈ 391`）、
> 门留在中线 `z = 105`（`y ≈ 408`，即原位置）。
> **上下间距仍是 `34 × 1.02 ≈ 35px`，错落感与初稿一致，但整体构图不位移。**

- 上下错开约 1/3 屏高，六个点位**仍然全部走得通**。
- **判定改成二维，但容差不是「贴到跟前才算」**：`zoneAt` 用
  `|Δx| ≤ reach && |Δz| ≤ reachZ`，`reach` 沿用原值（58–66，字段名不改，
  `tests/test_game_meta.js` 三处在读它），`reachZ = 60`。
  取 60 而不是更小的值，是因为 `reachZ = 30` 时场地前后各会留出一条
  「x 正对着设施、按 J 却什么都不发生」的死区（纵深 `z ∈ [0, 210]`，
  而上排可站位只有 `[92, 152]`、下排 `[58, 118]`）。取 60 后并集覆盖 `[28, 182]`，
  只有贴最前 / 最末边缘才不触发。**跨排误触不必担心**：相邻点位 x 间距 150–165
  大于相邻 `reach` 之和 116–124，x 轴本来就把它们分开了。
- **`reach` 要跟着 `z` 重新核一遍**：判定从 x-only 变成二维后，
  每个点位都必须实测一次「走到跟前能否触发、隔一个人身位能否不触发」。
- 错落之后**串门**（从上排走到下排）会不会撞到人物碰撞体也要看一眼。
- `x` 保持不变，避免破坏玩家已习惯的动线顺序。

### 5.5 音效

**现状核实：项目内零音频文件，且 `game/app.js:2609` 的
`audio: { noAudio: true }` 显式关闭了音频系统。这个决定已经把 Phaser 的
sound manager 判了死刑，不需要再探测。** 依据（读源码 + 实测双重确认）：

- Phaser 3.80.1 的 `SoundManagerCreator` 逻辑是
  `e.noAudio || (!i.webAudio && !i.audioData) ? new NoAudioSoundManager(...) : ...`。
  `noAudio: true` 走到 `NoAudioSoundManager`，它的 `play()` 就是
  `function () { return false }`，**永远返回 false 且不发声**。
- 实测：`game.sound` 这个对象**存在**（不会报错，容易误判成「能用」），
  但 `game.sound.noAudio` 是 `undefined`、`game.sound.context` 是 `null`。
  **`NoAudioSoundManager` 根本没有 `.context`**，所以
  「V19 去断言 `game.sound.context.state === 'running'`」这种写法会直接
  `TypeError`，**不是断言失败，是崩**。

**结论（不再留作待探测项）：自建 `AudioContext`，不用 Phaser 的 sound。**
理由是不可回避的：Phaser 侧已被配置切断，而 `noAudio` 只影响 Phaser 自己的
sound manager，**不会**阻止我们 `new AudioContext()`。两条路不冲突，
不存在「Phaser 占用了音频设备」的问题。

设计：

- 合成层是**自己的模块**（如 `game/audio.js`），持有唯一一个 `AudioContext`。
- **首次用户交互时创建/恢复**（`ctx.resume()`）—— 浏览器自动播放策略要求
  音频图必须在用户手势里启动，否则一开页面就静音且不报错。
- 所有音效是**按需创建节点、播完即弃**（oscillator / noise buffer 用完
  `stop()` 并让 GC 回收），不预建 17 条常驻音轨。
- `config.js` 只放参数（频率、时长、包络、增益），合成代码在 `audio.js`。
- 静音开关 = `masterGain.gain = 0`，**不要** `ctx.close()`（关掉就再也开不回来，
  且会打断已在播的音）。
- 模块级做**节流**：同一音效在极短时间（如 25ms）内重复触发要合并，
  否则连段攻击会在同一帧堆 3 个一样的音，听起来是爆音而不是三连击。

**音效清单（共 17 个，全部可调）：**

### V18 补充说明（原文只有表格一行，没有正文）

用户对这条的原话是「只要比每段攻击比之前大或远就行」，即**不能只放大基础范围**。
核实 `config.js`：连段范围在 `COMBO.steps`，当前三段是
**`58 / 62 / 74`**，另有 `ATTACK_RANGE = 62`、`ATTACK_DEPTH = 52`、
`ATTACK_BACK = 14`。

- 三段 `steps` 各自 **×1.05 以上**，且**必须逐段都变大** ——
  不能只改 `ATTACK_RANGE`（它只影响第一段的基准或非连段攻击）。
- `ATTACK_DEPTH`（纵深判定）与 `ATTACK_BACK`（身后判定）**跟着同比放大**，
  否则「范围变远了但砍不到侧面的敌人」，手感反而变差。
- 测试断言：三段 `steps` 都 `> 原值 × 1.05`，且 `ATTACK_DEPTH`、
  `ATTACK_BACK` 都 `> 原值`。

**经济漂移护栏（核实后修正：现成的 `tests/bot.js` 测不出这件事）：**

核实 `tests/bot.js`：`play(seed, difficultyId, upgrades, equipment)`（第 82 行）
每局都 `L.createState(seed)` **新建存档**（第 83 行），只设 `meta.equipment`
（第 93 行）就去 `L.startRun`（第 96 行）。它**从不出售、背包永远是空的**。
所以让它重跑一遍，跑的仍是和今天完全相同的路径 —— **它验证不了任何本批新增的
经济行为，这个「护栏」是假的**。问题不在担心，在仪器。

本批的正确做法：

1. **基线先冻**：把当前「零强化 `100/94/54/1`、半满 `100/97/89/26`、
   全满 `100/96/97/73`」当作改动前基线记录下来（本批不改战斗数值的假设下，
   重跑必须完全一致；**不一致说明碰到了不该碰的地方**）。
2. **给 bot 加出售能力**才是真护栏：让 `play()` 支持一个策略参数
   （如「攒满 N 件后按稀有度低→高卖」），这才测得出「删除 30% 自动退款 +
   玩家自行出售」对经济的影响。
3. **保守判据**：战斗数值改动（V18 的 +5%）本身就会抬高胜率，所以
   **任一档上升超过 8 个百分点**才叫经济变松；但若 V18 已生效，
   必须用**关闭 +5% 的开关**跑一遍对照，否则分不清是范围变大还是经济变松。
   （若实现者认为加开关成本过高，可退化为「只对比同一版本内不同策略」，
   但必须在文档里写明这条护栏被降级了，不能假装它还在。）

## 6.5 待 PM 确认的问题（不确认就不能开工）

以下是**设计里真的存在分岔、且选错要返工**的点。已核实的用「结论」给出答案，

### Q-PM-1. 战斗暂停：便宜的会漏刷新，正确的更贵

§4.8 的暂停有两个实现档：

- **便宜档**：`RunScene.update` 首行加早退。**副作用**：HUD 刷新、
  以及 `run.equipDrops` 的掉落提示排空（`app.js:1661-1672`）会一起冻住。
  玩家在暂停中卖掉一件刚落地的装备，提示与其结算顺序变成未定义。
- **正确档**：用 `this.scene.pause()`。DOM 浮层不受影响、继续可点，
  但**回调会打进已暂停的场景闭包**，这条必须写进文档而不是假装不存在。

**PM 已选：正确档（`scene.pause()`）。** 见 §4.8 的三个后果与成对 resume 要求。

### Q-PM-2. 删掉 30% 退款算不算改平衡？（是，而且 PM 拥有这个决定）

现在的规则：重复件立刻折算成 30% 铜币。删掉后，**从不打开背包的玩家收入
严格变少**（要到背包里手动卖才拿得回 50%，而且还得先花时间开包）。
这是**行为改变，不是纯 UI 增补**。

**PM 已确认：接受，并追加「批量出售」按钮**（规则见 §4.6.1）。
因此不需要额外的兜底提示 —— 批量出售本身就是那个出口。

### Q-PM-3. 「亏一半」亏的是什么？

§4.6 已核实：公式 `floor(0.5 × (基础价 + 已投入升级费))` 是**对升级费也打对折**，
所以升满的件卖掉亏掉全部投入的 50%。这是刻意防套利。

**PM 已确认：升级费也对折**，即永远亏掉全部投入的 50%。
「只亏基础价、升级费全返」的方案已被否决（那会让玩家靠反复升级/卖出套利）。

### Q-PM-4. 背包页数要不要跟着导出码走？

`meta.bagPages` 存在 `meta` 里，就会随 `profile.js` 的 `exportCode`/`importCode`
一起迁移（换设备/换浏览器导入时页数还在）。`profile.js` 本身没有
`STATE_VERSION`，所以这是**自动发生**而不是可选。

**PM 已确认：跟着走。** `meta.bagPages` 随 `exportCode`/`importCode` 迁移。

### Q-PM-5. 音效走 Phaser 还是自建 AudioContext？

**已核实并定论，不需要 PM 选**：`app.js:2609` 的 `noAudio: true` 让 Phaser
拿到的是 `NoAudioSoundManager`，`play()` 恒返回 `false`，且**没有 `.context`**。
所以自建 `AudioContext` 是唯一可行路径，且与 Phaser 不冲突。详见 §3.5-音频段
与 §5.5。
