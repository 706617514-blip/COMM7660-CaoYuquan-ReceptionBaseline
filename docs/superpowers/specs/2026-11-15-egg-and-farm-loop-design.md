## 1. 意图与理由

### 1.1 这次要解决的真正问题

游戏现在**没有终点**。三档 Boss（普通/困难/地狱）打完**毫无区别**——不掉东西、不记录、不改变任何状态。玩家把游戏"玩到头"之后，**游戏不知道这件事，玩家也拿不到任何东西**。

同时，**农场是一个孤岛**：`C.FARM.yieldPerPlot = 9` 只产铜币，种出来的东西除了卖钱没有第二个出口。PM 的设计初衷是「农场是装点小世界的场地，收获的东西可以吃下去加血」，但这条线现在**完全不存在**。

这两件事合起来是一个问题：**游戏有内容，但没有形成闭环**。

```
现在的循环：  远征 → 铜币/装备 → 变强 → 远征  （农场在圈外）
目标循环：   远征 → 铜币/装备/种子 → 变强 ─┐
                  ↓                        │
               农场 → 收获 → 吃下去 ────────┘
                  ↓
           打通熔炉 + 打赢地狱 Boss → 彩蛋（终点）
```

### 1.2 为什么现在做

1. **终点立起来，游戏才有"打完"的概念。** 这是当前最扎眼的结构空洞。
2. **彩蛋是 PM 自己写的一句话**，是这个项目里最有个人色彩的地方，早做早有位置。
3. **第 1 步（切 WebGL）本来就该做**——它同时解决 PM 反馈的"画面平"。现在它有了硬理由：Canvas 混合模式做不出全屏泛光。

### 1.3 成功的样子

PM 玩一局，能把这条路径走完：

> 在基地种下从远征带回来的花 → 收获 → 带着补给去打熔炉并通关 →
> 挑战地狱 Boss 并打赢 → **Boss 尸体上浮起一颗七彩蛋** → 按 J → 全屏光爆 →
> 纸条渐现 → 回基地，**纸条挂在墙上**，随时能再看

### 3.3 已确认的技术事实（侦察所得，非推测）

```js
// game/app.js:1129
const BOSS_TIER_DIFF = { normal: 'wood', hard: 'deep', hell: 'forge' };
```

**⚠️ 这里有一个已修正的错误，实施时必须按修正后的写法。**

本文档初稿曾断言：「地狱 Boss 在地狱档时难度被设成熔炉，所以两个条件是同一个状态」。
**这个断言是错的**，由独立构建者审查（2026-11-15）发现，我已复核确认：

`startBossRun('hell')` 确实调用 `startRun(state, 'forge')`（`app.js:2152`），
于是 **Boss 局的 `run.difficultyId` 就是 `'forge'`**。
若"通关熔炉"成就用 `difficultyId === 'forge'` 判定，**打赢地狱 Boss 会同时把两个成就置位**，
PM 要求的"两个成就"当场坍缩成一个条件，彩蛋逻辑失效。

**正确判定（`!run.isBossRun` 不可省略）**：

| 成就 | 判定条件 | 说明 |
|---|---|---|
| 通关熔炉 | `!run.isBossRun && run.difficultyId === 'forge' && won` | **必须排除 Boss 局** |
| 打赢地狱 Boss | `run.isBossRun && run.bossTier === 'hell' && won` | Boss 局走独立路径 |

| 判定点 | 位置 | 机制 |
|---|---|---|
| 通关熔炉 | `logic.js:2037` `stepWave()` | `run.waveIndex >= run.diff.waves` → `endRun(state, true)` |
| 打赢地狱 Boss | `logic.js:1728` `killEnemy()` | `e.isBoss` 死亡。**Boss 局不走 `stepWave`**（`breakTimer = 99999` 冻住波次） |
| 击杀位置 | `killEnemy` 的 `e.x, e.z` | 掉落物已用这对坐标做抛物线 |
| 拾取 | `logic.js:1786` `stepPickups()` | 现有 pickups 数组，`grounded` 后才能捡 |
| 存档 | `logic.js:2201` `serialize()` | `meta` 加字段有 `uidSeq`/`ambient` 先例 |

**结论：两条胜利路径是两个独立位置，必须分别挂判定。**

## 4. 方案与取舍

### 4.1 彩蛋触发：怎么记录"两个成就"？

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A. 两个布尔标记**（选定） | `meta.clearedForge` + `meta.beatHellBoss`，任一置位时检查另一个 | **简单、可读、存档小。** 两个成就本来就是两个独立事实，各自一个布尔最诚实 |
| B. 单一 `eggFound` + 前置检查 | 只记彩蛋状态，触发时现场判断 | 无法区分"只通关了熔炉"和"什么都没做"，成就展示会缺信息 |
| C. 成就系统（通用） | 建一个成就表，彩蛋是其中一个 | **过度设计**。为两个标记建一套系统，维护成本远超收益 |

**选 A**，理由：两个成就各自独立，各自一个布尔字段，判断逻辑就是一次 `&&`。将来要加成就展示，这两个字段直接可用。

### 4.2 彩蛋掉落：挂在哪？（**本节含一个必须处理的陷阱**）

**PM 已确认：掉落点是"触发那一局的最后一个敌人死亡的位置"。**

| 情形 | 触发点 | 落点 |
|---|---|---|
| 先通关熔炉 → 后打赢地狱 | `killEnemy` 的 Boss 分支 | 地狱 Boss 尸体位置 |
| 先打赢地狱 → 后通关熔炉 | `stepWave` 的 `endRun` 之前 | **熔炉最后一只怪**的尸体位置 |

**这里有一个实现细节必须处理**：`stepWave` 触发通关时，最后一只怪已经在 `killEnemy` 里死了，`e.x/e.z` 需要被记住。

**做法**：在 `killEnemy` 里**无条件**记录 `run.lastKillX / run.lastKillZ`（两行赋值，无副作用）。这样两处触发点都能取到"最后一个敌人死在哪"。

> 这是本设计里唯一一处需要改 `logic.js` 既有函数的改动，且它是纯增量（只写两个新字段，不读不判断）。

---

#### ⚠️ 陷阱：`collectAll` 会把蛋吸走（构建者审查发现，已复核确认）

**事实链**（三处均已核实）：

1. `logic.js:2027` —— `stepWave()` 清波时调用 **`collectAll(state, run)`**
2. `logic.js:1820` —— `collectAll` 把 **`run.pickups` 里所有掉落物一次性吸进战利品**
3. `logic.js:701-702` —— `stepPickups` 还会自动吸附 `grounded` 且进入 `pickupRadiusX/Z`（40/34）的任何掉落物

**后果**：若把彩蛋做成普通 pickup 推入 `run.pickups`，则"先打赢地狱 → 后通关熔炉"这一顺序下：

```
熔炉最后一只怪死
  → stepWave 检测到 alive === 0
  → collectAll 把所有 pickups 吸走（含彩蛋！）
  → endRun 结算，进入结算界面
  → 玩家永远没有机会按 J
```

**"按 J 拾取"会看起来实现了，实际根本触发不到。** 这是本设计最可能的实现陷阱。

**同时它暴露了 PM 设计里的一个真实漏洞**（已由 PM 裁决为 D5）：

> 熔炉通关后不立刻结算，先让玩家走过去按 J 捡蛋，捡完再结算。

---

#### 彩蛋的正确实现方式（D5 裁决后）

**彩蛋不是普通 pickup，而是 `run.egg` 独立对象**，理由是它必须**免疫 `collectAll` 与自动吸附**：

| 属性 | 值 | 理由 |
|---|---|---|
| 存放 | `run.egg = { x, z, state: 'ground' }` | **不放进 `run.pickups`**，从根上避开 `collectAll` |
| 自动吸附 | **无** | PM 指定"按 J 拾取"，自动吸走会让指定动作失去意义 |
| 拾取判定 | 玩家在 `run.egg` 附近时，**按 J** 触发 | 复用既有 `KeyJConfirm` |
| 超时 | **不消失** | 它是彩蛋，不是掉落物 |

**熔炉通关的流程改造（D5 / 涉及 `logic.js` 既有行为，风险最高的一处）**：

```
现状：  stepWave 检测通关 → endRun(state, true) → phase = 'result'

改为：  stepWave 检测通关
          → 若 应掉彩蛋（两成就齐全且未掉过）：
              生成 run.egg 于 lastKill 位置
              run.pendingEggSettlement = true
              **不调用 endRun**，phase 保持 'run'（玩家可走动）
          → 玩家按 J 拾取 run.egg
          → 拾取后（演出结束）才调用 endRun(state, true)
          → 若 不该掉彩蛋：行为完全不变，直接 endRun
```

> **风险声明**：这是本次唯一**修改既有胜利路径**的改动。它会影响"通关熔炉"的所有既有测试。
> 实施时必须：① 先写测试锁住"两成就不齐时行为完全不变"；② 跑 `bot.js` 确认平衡未漂。

### 4.3 全屏泛光：为什么必须先切 WebGL

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A. 切 `Phaser.WEBGL`**（选定） | `app.js:4206` 一行改 | **能用真泛光**（叠加混合 + 光源），但需全量回归 38 处程序化贴图 |
| B. 留在 Canvas，用渐变色块伪造泛光 | 画一个径向渐变大圆 | 零风险，但**做不出《头号玩家》那种光爆**，PM 要的效果达不到 |
| C. 切 WebGL 但保留 Canvas 回退 | `Phaser.AUTO` | **不可控**——`AUTO` 在支持 WebGL 的浏览器上仍会选 WebGL，回退路径不会被测试覆盖，等于假装有保险 |

**选 A**，理由：**PM 要的效果只有 WebGL 能做**，且 WebGL 同时改善"画面平"。C 是伪保险，不做。

**风险与对策**：切 WebGL 后，38 处 `generateTexture` 和所有资产都要重新验证。对策见 §5.1 的两道闸门，**任何一处异常就回退**。

**实施前实测的三条风险情报**（2026-11-15 核实，非推测）：

| 发现 | 事实 | 影响 |
|---|---|---|
| **8 处 `BlendModes.ADD`** | `app.js:1723/1751/1753/1755/1769/1789/2696/3964`，**全部是发光效果**（火星、光晕） | ⚠️ **这是最大风险点**。ADD 在 Canvas 与 WebGL 下渲染不同（WebGL 受预乘 alpha 影响），必须逐处目视确认 |
| `sprites.js` 的 `getContext('2d')` | 用的是**独立离屏 canvas**（`doc.createElement`），不是 Phaser 渲染器，只做像素测量与 `toDataURL` | ✅ **风险解除**：与渲染器无关，不受切换影响 |
| `sprites.js` 的兜底 | `if (!ctx) return null`、`if (x1 < 0)` 退回整图、`fitUrl` 收异常为 null | ✅ 该模块在异常环境下安全 |

**推论**：WebGL 切换的真实风险**集中在 8 处 ADD 混合**，而不是 38 处 `generateTexture`（后者是 Phaser 统一 API，行为跨渲染器一致）。§5.1 闸门二的核对表**必须点名这 8 处**，逐一截图对比。

### 4.4 农场循环：作物怎么变成补给？

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A. 作物种类 + 直接食用**（选定） | 加 3–4 种作物，收获物进背包，可"吃"（回血/临时增益） | **复用现有药水机制**（`POTIONS` 已有 `instant`/`buff` 两种 kind），改动集中 |
| B. 作物 → 加工 → 成品（两步） | 收获物先加工成补给 | 更深的经营，但**多一层 UI 和多一层状态**，本次范围会失控 |
| C. 作物只加数值不加机制 | 收获物 = 另一种铜币 | **不解决 PM 的初衷**（"吃下去加血"），等于没做 |

**选 A**，理由：PM 的初衷是"收获的东西可以作为补给吃下去加血加体力"。**甲方案要求不要体力**，所以只剩"回血 / 临时增益"，而这两样 `POTIONS` 现成。

**作物怎么来？** PM 说"远征捡回来的花、农作物"。现有 `LOOT.seedChance` 已经在掉种子——**扩展成"掉特定作物的种子"即可**，不新建掉落系统。

## 8. 独立应用外壳（D9）

**PM 的最终目标是独立应用，不是网页版。** 因此本次**先把 Electron 外壳搭起来，之后的功能都在壳里开发**。

### 8.1 为什么现在就搭

| 理由 | 说明 |
|---|---|
| 环境正确性 | 在壳里开发，**任何一个"只在浏览器里能跑"的写法会立刻暴露**，而不是留到最后 |
| 存档形态 | 浏览器是 `localStorage`，独立应用应能读写文件。**早做早统一** |
| 音频策略 | 浏览器的自动播放限制在独立应用里不存在，**可以去掉一部分兼容代码** |

### 8.2 已核实的环境事实（2026-11-15 实测）

| 项 | 状态 |
|---|---|
| `node` | ✅ v24.21.0 |
| `pnpm` | ✅ 10.34.5 |
| `npx` | ✅ 可用 |
| `npm` | ❌ 不存在（用 `pnpm` / `npx` 替代） |
| npm registry | ✅ HTTP 200，0.15s |
| GitHub（Electron 二进制） | ✅ HTTP 200，1.13s |
| npmmirror 镜像 | ✅ HTTP 302（正常镜像跳转），0.30s |

**结论：Electron 的下载与安装路径是通的**，且国内镜像可用（如 GitHub 慢，可切 `ELECTRON_MIRROR`）。

### 8.3 存档层的既有优势（侦察所得，非推测）

`profile.js` 的文件头写着：

> 「纯模块：不碰 DOM、不碰 localStorage，**存储对象由调用方注入**，因此可测。」

**这意味着换到文件存储只需要换一个注入对象，游戏逻辑一行不改。** 而且它已有「可导出的存档码」机制（换设备搬移进度），**这个设计在独立应用里同样成立，甚至是加分项**。

### 8.4 约束（本次所有改动都必须遵守）

| 约束 | 理由 |
|---|---|
| **不得引入新的浏览器专有依赖** | 如 `window.open`、依赖 HTTP 服务器才能工作、写死 `http://` 资源路径 |
| **资源路径必须相对** | 独立应用走 `file://`，绝对路径会 404 |
| **存档层不得写死 `localStorage`** | 保持 `profile.js` 的注入式设计，为文件存储留口 |
| **不依赖外部网络** | 独立应用应能离线运行 |

### 8.5 外壳的验收判据

| # | 判据 |
|---|---|
| E1 | 双击应用图标能启动，直接进游戏（不是终端里跑命令） |
| E2 | **离线可用**（拔网线仍能玩） |
| E3 | 存档写入本地文件，重启应用后进度还在 |
| E4 | 窗口可调大小，画面自适应 |
| E5 | 现有的 12 个测试套件在壳里同样通过 |

> **E1/E2 是"独立应用"这个要求的字面判据** —— 如果做不到双击启动 + 离线可用，那它就还是个网页。
