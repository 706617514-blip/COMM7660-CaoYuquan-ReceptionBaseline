## 1. 一句话概括

**把「星露谷物语」的经营与「熔炉密林」的横版肉鸽动作，压缩成一个可循环的最小核心。**

玩家在一个横版场景里打怪 → 掉落的种子和铜币带回基地 → 种田产生**每局被动收入**、或直接买强化**立刻变强** → 再下地打更难的。

核心循环只有一条：

```
战斗（约 40–60 秒）→ 收获种子/铜币 → 农场经营 + 购买升级 → 变强 → 再战斗（更难）
```

## 2. 设计原点与约束（为什么是现在这个样子）

这一节很重要——它解释了**所有取舍的原因**，不理解这一节就会觉得很多设计莫名其妙。

### 2.1 需求来源

用户（PM）的原话要求是：

> 「能不能做一个 2D 的横版经营闯关动作类游戏，把**星露谷物语（经营种地）**和**熔炉密林（横版肉鸽动作）**这两种类型的游戏结合」

同时被否决的第一版方案是**不做**——原来的 Phase 2 产品是一个「Steam 口碑基准分析网站」，教授反馈说它「实际用处几乎可以忽略不计」，要求「根据数据分析工具选出一个类型的游戏去开发制作」。

### 2.2 硬约束：时间与作业要求

**完整的「星露谷 + 熔炉密林」是 2–3 年、一个团队的项目。** 交付窗口只有 **13 天**（2026-11-06 → 11-19），单人。

所以关键决策不是「缩小地图」，而是：

> **把整个游戏压缩成一个循环。**

作业原文（Assignment One）对产出的要求是：

> "A **short playable level or core loop**—the repeated sequence of actions and feedback—with instructions, meaningful interaction, an outcome, and restart."

原文还有一句必须复述的评分约束：

> "Complexity, tool count, dataset size, and **visual polish alone earn no marks**."

**这条直接决定了美术策略**：用几何图形和程序生成纹理，不做像素图；力气全花在**手感**（按键响应、打击反馈、数字跳动）而不是画面上。

### 2.3 数据驱动的题材选择

品类不是拍脑袋选的，是先做了 Steam 市场分析（Phase 1，486 款作品、9 个品类、24 个月窗口）。关键结论：

| 标签 | 存量作品 | 触达率（≥100 条评论） | ≥1000 条 | 有评论者中位 | 中位好评 |
|---|---|---|---|---|---|
| **Roguelite** | **15,215** | **22.2%** | **7.4%** | 71 | 81% |
| **Farming Sim** | **2,582** | **22.2%** | 3.7% | 70 | 78% |
| Simulation | 56,247 | 22.2% | 5.6% | 103 | 76% |
| Indie | 123,538 | **5.6%** | 1.9% | 26 | 92% |

**决策依据**：Roguelite 的触达率最高、上限最高（≥1000 条占 7.4%，全样本最高），而拥挤度只有 Simulation 的 1/3；Farming Sim 拥挤度只有 Simulation 的 1/22。Indie 是结构性红海，排除。

⚠️ **必须诚实说明的一点**：各品类的差异**统计上不显著**（口碑 p = 0.400、触达 p = 0.297）。所以上面的选择**不是「因为数据证明 Roguelite 更好」**，而是「Roguelite 的点估计方向最好、且单人 13 天可行」。

## 3. 核心循环的详细设计

### 3.1 三层结构

```
┌─────────────────────────────────────────┐
│  基地（Hub）— 可走动的场景，不是菜单      │
│  走到设施前按 J 交互                      │
└─────────────────────────────────────────┘
        ↓ 走到「远征之门」按 J 选难度
┌─────────────────────────────────────────┐
│  战斗（Run）— 2.5D 横版竞技场             │
│  三/四波敌人，清完为胜，血空为败           │
└─────────────────────────────────────────┘
        ↓ 结算：种子 + 铜币（失败保留一半）
┌─────────────────────────────────────────┐
│  农场（Farm）— 独立场景，淡入淡出          │
│  3×3 田地，种下后 2 局成熟，之后每局产出    │
└─────────────────────────────────────────┘
        ↓ 回到基地，变强，再出发
```

### 3.2 为什么「种田」和「肉鸽」是真连起来的

这是设计上最容易做砸的地方——如果两层各自独立，就只是「两个弱小的迷你游戏拼在一起」。

**连接点是经济**：

> **种田产出的是「以后每局都变强」的被动收入；买强化是「立刻变强」。**

核心张力只有一句话：

> **种子稀缺时，是种下去（延迟、复利），还是买强化（立刻见效）？**

这一个张力就是「经营」的本质。两句话能说清，代码量很小。

### 3.3 农场的具体规则

从 `game/config.js` 的 `FARM`：

| 字段 | 值 | 说明 |
|---|---|---|
| `cols × rows` | 3 × 3 | 一页 9 块 |
| `runsToMature` | **2** | 种下后满 2 局成熟 |
| `yieldPerPlot` | **9** | 每块成熟田每局产 9 铜币 |
| `seedCost` | 1 | 每块田消耗 1 颗种子 |
| `plotPrice` | 3000 | 开垦新田地单价 |
| `perPage` | 9 | 每页 9 块（3×3 透视布局不随块数变） |
| `maxPlots` | **27** | 最多 3 页 |
| `seedSpoilRate` | 0.25 | 超额种子每局腐烂 25% |
| `runDecayChance` | 0 | 作物枯萎（**当前关闭**，避免惩罚过重） |

**三个关键设计点**：

1. **按「局」计龄，不按时间。** 所以**失败也有进展**——玩家不会卡死。`endRun` 里无论胜负都执行 `plot.growth += 1`。
2. **种子失效机制**：`meta.seeds` 是单一整数，玩家没有上限地囤种子，而田地有限，囤积没有任何用途——只是数字变大。所以超过「自家田地数」的那部分每局腐烂 25%。
   - **grace 值取当前田地数**：田地是种子的唯一去处，所以「够种满自家所有田」永远不该被吃掉。满田玩家不会断种，只有真正的超额囤积才衰减。
   - 用**按比例腐烂**而不是「每颗种子有寿命」：带年龄的列表要动存档结构、迁移链和所有读取点，收益与风险不成比例。
3. **田地页数不单独存**，由 `plots.length` 推导（`ceil(块数 / perPage)`）。这样「田地被加了一块」和「多了一页」永远是同一个事实，不会漂移。

**回本周期**：一块地 3000 铜币、每局 +9，约 **334 局**回本。这是**长线目标**，不是随手可买的小道具。

## 4. 战斗系统

### 4.1 坐标系（这是整个游戏的技术根基）

游戏是 **2.5D**，`logic.js` 里一直是**三轴**：

| 轴 | 含义 | 范围 |
|---|---|---|
| `x` | 水平位置 | 0 – 960（`FIELD_W`） |
| `z` | **景深**（地面带内的前后位置） | 0 – 210（`FIELD_D`） |
| `h` | 离地高度（跳跃用） | 0 = 站在地上 |

渲染时 `z` 表现为屏幕上的竖直偏移。`GROUND_Y = 515` 是 `z = 0` 时的地面基线。

**关键设计**：**命中判定必须同时用 `(x, z)` 两个轴**——只有 x 重叠而 z 差太多时**不该命中**。

> 这是 beat-em-up 的惯例，也是 W/S 深度轴存在的意义。
> 没有这条判定，W/S 只是装饰，游戏就退化成纯横版。

⚠️ **如果 3D 化，请注意**：坐标已经是 `(x, z, h)` 三轴，**36 处引用**。也就是说规则层本来就是为了真 3D 设计的。

### 4.2 玩家基础值

| 常量 | 值 |
|---|---|
| `BASE_HP` | **70** |
| `BASE_DAMAGE` | **12** |
| `BASE_ATTACK_SPEED` | 1.0 |
| `PLAYER_SPEED` | 250 px/s |
| `PLAYER_DEPTH_SPEED` | 150 px/s（比水平慢，符合视觉惯性） |
| `JUMP_V` | 430 |
| `GRAVITY` | 1500 |
| `INVULN_AFTER_HIT` | 0.8 s |
| `WAVE_HEAL` | **18**（清波回血） |

> `WAVE_HEAL` 的来源是一个真 bug：**没有回血机制时，长局在数学上不可能通关**——这不是「难」，是设计错误。

### 4.3 三段式普攻（连击）

节奏是 **快 → 快 → 慢**：第 1、2 段出手极快，用来贴上去压血；第 3 段是收招，伤害与击退都明显更高，但硬直长，**打空就会被惩罚**。

连击窗口内再次按下才接续；超时回到第 1 段。窗口 `COMBO.window = 0.55` s。

| 段 | 伤害倍率 | 冷却 | 射程 | 击退 | 硬直 |
|---|---|---|---|---|---|
| 1 | 1.00 | 0.26 | **73** | 120 | 0.10 |
| 2 | 1.15 | 0.28 | **78** | 180 | 0.12 |
| 3 | **1.85** | **0.62** | **90** | **460** | 0.34 |

**射程下限由「体型最大的敌人」决定，不是由小怪决定**——这是一个踩过的坑，见 §4.7。

其他攻击常量：`ATTACK_RANGE = 78`（兜底）、`ATTACK_DEPTH = 55`、`ATTACK_BACK = 15`（身后也蹭到一点）、`ATTACK_DURATION = 0.16`。

### 4.4 冲刺

| | 步行 | 冲刺（按住 Shift） | 倍率 |
|---|---|---|---|
| 水平（A/D） | 250 px/s | 405 px/s | **1.62×** |
| 深度（W/S） | 150 px/s | 190 px/s | **1.27×** |

**深度轴倍率故意更收敛**——如果前后也用 1.62 倍，瞄准会变得很滑，躲弹道反而更难。

**松开立刻回到步行，没有任何惯性**。这点是刻意的：冲刺如果会滑行，玩家就没法精确停在攻击距离上。

### 4.5 五个技能

键位：**U / I / O / K** 是基础技能，**L 是大招**。

```
裂风斩(朝前长条) ≠ 普攻(近距离矩形) ≠ 震地(环形)  —— 三种形状彻底分开
```

| 键 | 技能 | 冷却 | 伤害 | 满级 | 射程/半径 | 定位 |
|---|---|---|---|---|---|---|
| **U** | 裂风斩 | 5.6 → 4.7 | 26 → 62 | 5 | 前方 190 × 深 74 | 贯穿一整排 |
| **I** | 闪现 | 4.0 → 3.3 | 10 → 26 | 5 | 位移 200 | 脱身 + 无敌帧 0.40s |
| **O** | 震地 | 8.0 → 6.8 | **16 → 40** | 5 | 半径 132 | **解围**：击退 1050 + 硬直 0.60s |
| **K** | 战吼 | 13.0 → 11.2 | 治疗 22 → 62 | 5 | — | 回血 + 6s 增伤 35% |
| **L** | 熔野爆发 | 26.0 → 24.0 | **45 → 89** | 3 | 半径 2000 | 大招，全屏 |

**设计意图**：玩家反馈「整体没有难度」，而单纯加血加伤只会变成互相磨。**技能给的是「应对手段」**——闪现脱身、震地解围、战吼续命、大招收尾。难度因此来自「**要不要用、什么时候用**」，而不是数值对撞。

**震地的一个反直觉发现**（重要）：只把击退数值翻倍，实测小怪只被推开 **19px**——因为它**每帧都在往玩家走，把击退吃掉了**。真正起作用的是加了**硬直**：被击退期间不走位。实测位移从 19px 变成 **114px**。

> **教训**：击退系统的实际手感由「硬直」而非「冲量」决定。

### 4.6 三种敌人

只有三种，但**行为完全不同**，目的是用最少的内容撑起区分度。

| | 爬虫 | 冲刺虫 | **吐酸虫** |
|---|---|---|---|
| 行为 | `chase`（直线追，两轴都跟） | `lunge`（蓄力后直线冲） | `ranged`（保持距离吐弹） |
| HP | 42 | 30 | 24 |
| 接触伤害 | 10 | 14 | 8 |
| 速度 | 92 | 126 | 78 |
| 半径 | 18 | 16 | 17 |
| 击退系数 | 1.0 | 1.4 | — |
| 参数 | — | 蓄力 0.55s、冲速 430、冲时 0.32s | 保持 250px、冷却 2.3s、抬手 0.65s |

**吐酸虫是设计上最关键的一种怪。** 它存在的意义不是「多一种怪」，而是**打破「一直往后跑就安全」的解法**：

| 弹道属性 | 值 |
|---|---|
| 速度 | 275 |
| 伤害 | 11 |
| 命中宽度（x） | 20 |
| **命中深度容差（z）** | **26** |
| 存活 | 3.0 s |

**关键**：弹道**只覆盖一条深度线**。站桩必中，但**换深度就能躲开**。

> 这让深度轴第一次从「能走动」变成「**必须走位**」——这是整个 2.5D 设计成立与否的关键。

三种敌人形成配合：**爬虫压位置、冲刺虫惩罚站桩、吐酸虫逼你换深度。**

### 4.7 Boss：藤蔓巨像

**三个设计约束**：

1. **移动极慢**，靠贴身普攻与技能施压，而不是追击（速度 **26**，小怪是 92–126）
2. **技能范围分层**：2 近身 + 2 范围（直径 ≤ 半屏 480px）+ 1 全屏
3. **全屏技能必须有前摇**，且前摇长到可以用闪现躲开

#### 两个半径必须分开（这是踩过的坑）

| 字段 | 值 | 含义 |
|---|---|---|
| `hitRadius` | **74** | **受击半径（hurtbox）**：玩家的刀能碰到多远 |
| `bodyRadius` | **46** | **碰撞半径（body）**：玩家身体被推开到多远 |
| `radius` | 46 | 兼容字段，等同 `bodyRadius` |

> **这个分离解决了「要完全贴住 Boss 才能打到」的缺陷。**
>
> 以前共用一个 `radius: 46`，于是「把 hitRadius 调大让更好打中」会**同时把玩家推得更远，反而更难打到**（自相矛盾）。
> 玩家被推开 `minGap = 46 + 17 + 6 = 69px`，三段射程只有第三段能覆盖。现在受击半径 46 → 74，站在 minGap 上时有效距离等于 `range + 74 - 69 = range + 5`，三段都留出余量。
> 小怪的 `minGap` 只有 39–41，所以这个缺陷**只在 Boss 身上暴露**。

#### 三档难度（对应装备门槛）

| 档 | HP | 伤害 | 速度倍率 | 冷却倍率 | hint |
|---|---|---|---|---|---|
| `normal` 普通 | 1400 | 18 | 1.00 | 1.00 | 次顶级装备可艰难通过 |
| `hard` 困难 | 2400 | 26 | 1.15 | 0.85 | 顶级装备可艰难通过 |
| `hell` 地狱 | 4000 | 36 | 1.30 | 0.70 | 全套装备且熟练使用技能 |

基础参数：`speed: 26`、`attackCooldown: 3.1`（2.4 时出手过密，玩家读不到节奏）、`meleeRange: 96`。

#### 五个技能

| id | 名称 | 类型 | 伤害 | 半径 | 前摇 | 冷却 | 备注 |
|---|---|---|---|---|---|---|---|
| `slam` | 碾压 | 近身 | 26 | 120 | 0.55 | 5.8 | 击退 380 |
| `grab` | 缠绕 | 近身 | 22 | 140 | 0.40 | 8.1 | 硬直 0.8s + 拉向自己 90 |

#### 程序化手臂（避免「一张贴图在平移」）

Boss 本体是三张 PNG 躯干（三档各一对左右视图），只在做 `setPosition` —— **看起来像一张贴图在平移，很诡异**。

修法是保留 PNG 当躯干，在独立 Graphics 层上按状态画**两条分节藤蔓手臂** + 呼吸/起伏/倾角（姿态在 `game/bosspose.js`）。

| 参数 | 值 | 说明 |
|---|---|---|
| `armSegRatio` | [1.0, 0.86, 0.74, 0.63, 0.54, 0.46] | 六节长度比，累加 ≈ 4.23 |
| `armBaseLen` | 0.085 | 第 1 节 = 0.085 × 贴图高 |
| `armWidthRoot` / `armWidthTip` | 10 / 4 | **必须乘 scale 再画** |
| `armColorRoot` / `armColorTip` | 0x7a6a55 / 0x5c4c3e | **必须比本体亮**（本体实测 0x4a4038） |
| `armAnchorX` / `armAnchorY` | 0.36 / 0.42 | 锚点在轮廓**内部** |
| `armSpread` | 0.42 rad (≈24°) | 张开角度 |
| `stepPeriod` | 0.62 s | 步态周期 |

**两个必须知道的坑**：
1. 三档贴图高度不同（321 / 407 / 403），都缩到 185px 高，**不乘 scale 手臂会一档长一档短**。
2. 线宽 7/2.5 时落屏只有 3.6→1.3 CSS px，**比躯干自己那团藤蔓还细，1x 下根本读不出手臂**。改成 10/4 落屏 5.2→2.1 px。

## 5. 难度系统：用「档」代替「关卡数」

**这是本作最重要的一个设计决策。**

不做关卡树、不做地图选择。改为 **4 档难度 × 不同小怪数值**，而**战利品倍率随难度上升**：

| id | 名称 | HP 倍率 | 伤害倍率 | 速度倍率 | 波数 | 基础数量 | **战利品倍率** | 刷怪间隔 |
|---|---|---|---|---|---|---|---|---|
| `grass` | 草丛 | 0.85 | 0.70 | 0.90 | 3 | 4 | **1.0** | 1.50 |
| `wood` | 林地 | 1.32 | 1.26 | 1.02 | 3 | 5 | **1.7** | 1.35 |
| `deep` | 密林 | 1.75 | 1.45 | 1.14 | 4 | 6 | **2.5** | 1.15 |
| `forge` | 熔炉 | 2.10 | 1.75 | 1.20 | 4 | 7 | **3.5** | 1.05 |

**`lootMul` 是最关键的字段**：难度越高，战利品倍率越高。这让玩家必须决定「**稳着种田**」还是「**冒险推进**」——**这就是本作的经济张力。**

### 5.1 每波构成

```js
function waveComposition(waveIndex, diff) {
  const n = diff.baseCount + waveIndex;
  const runnerShare  = min(0.55, 0.15 + waveIndex * 0.12);
  const spitterShare = waveIndex >= 1 ? min(0.34, 0.14 + (waveIndex-1) * 0.10) : 0;
  // crawler = 其余的
}
```

吐酸虫从第 2 波（`waveIndex >= 1`）开始出现，比例随波次上升。

### 5.2 刷怪分批发

```js
SPAWN = { burstSize: 3, burstGap: 2.6 }
```

一次全涌出来会让每波变成「站桩清场」。改成 **3 只一批、批间停顿**，战斗就有了推进感。

### 5.3 实测平衡曲线（可由脚本复现）

`node tests/balance_report.js` 生成，**阶梯必须单调递减**（有断言保护）：

## 6. 经济系统

### 6.1 铜币的四个去处

```
铜币 ──┬─→ 铁匠铺升级（基础属性）
       ├─→ 兵器架：买装备 / 升级装备（独特机制）
       ├─→ 技能祭坛（技能等级）
       ├─→ 商店：药水（消耗品）+ 开垦田地 + 背包页
       └─→ （被动）农场产出 ←── 这是唯一「钱生钱」的路径
```

### 6.2 铁匠铺：三个基础强化

**幅度刻意压平：满级约等于基础值的 2 倍，不是 3 倍。**

> 早期版本是 +3 伤害 / +25 血 / 8 级，全满时伤害与血量都是 3 倍，结果「中期强化」就让四档难度**全部变成 100% 通关**——难度选择失去意义，**经营层反而吃掉了整个游戏的核心张力**。

| id | 名称 | 效果 | 基础价 | 成长 | 满级 | 每级 |
|---|---|---|---|---|---|---|
| `damage` | 锋刃 | 每次攻击 +2 伤害 | 25 | 1.42 | 6 | +2 |
| `maxHp` | 耐力 | 生命上限 +12 | 30 | 1.40 | 6 | +12 |
| `speed` | 轻步 | 移动速度 +4.5% | 28 | 1.48 | 4 | +4.5% |

### 6.3 兵器架：装备系统

**定位（方案 C）**：铁匠铺管**基础属性**，装备管**独特机制**。

> 如果装备只是「第三个加属性的地方」，三层就退化成同一件事，玩家只会比较数字大小——那是最省事也最没有内容的设计。

#### 三条不变量（改数值时必须一起检查，测试里有对应断言）

1. **特效装备价格挤在 680–900**：让玩家**按打法选**，不是按数值选
2. **任何装备的等效强度不超过同部位基础装备的 1.3 倍**，防止唯一最优解
3. **特效装备升级只提升「强度参数」，绝不改变机制本身**——反伤 30%→34%→38% 永远是「反伤」

#### 基础装备：16 件（5 部位 × 3–4 档）

## 7. 战利品与结算

### 7.1 掉落

| 字段 | 值 | 说明 |
|---|---|---|
| `coinsPerKill` | 4 | 每只小怪基础掉落（再乘难度 `lootMul`） |
| `seedChance` | **0.05** | 每只小怪掉种子的概率 |
| `clearBonusCoins` | 20 | 清完一波的额外奖励 |
| `lossKeep` | **0.5** | 倒下时保留的战利品比例 |
| `pickupLife` | 16 s | 掉落物存在时间 |
| `pickupRadiusX` / `pickupRadiusZ` | 40 / 34 | 拾取范围 |
| `pickupGravity` | 620 | 掉落物弹出的重力（决定手感） |

### 7.2 「掉落需走过去捡」是节奏设计

> 以前击杀铜币**自动入账**。现在掉在地上：**打 → 扫战场捡东西 → 下一波**。

这条改动还带来一个正面副作用：**清波时会自动收走剩余掉落**，所以不会出现「清完场却丢了战利品」的憋屈感。

### 7.3 三条结算路径（都在 `endRun` 里）

| 路径 | `keep` | 说明 |
|---|---|---|
| **通关** | 1.0 | 全额 |
| **倒下** | `LOOT.lossKeep` = 0.5 | 保留一半 |
| **主动退出战斗** | 按剩余血量折算 | **要求四舍五入**（`Math.round`） |

> 早退是玩家主动做的决定，不该像战败那样把他本就不多的一半**再往下抹一次零**。

**三条路径的共同动作**：
1. 铜币/种子入账（乘 `keep`）
2. `runsCompleted++`，胜利则 `runsWon++`
3. **种子失效**（超过田地数的部分腐烂 25%）
4. 药水同步：**用「剩余量回写」而不是「扣减量」**，中途重开也不会重复扣
5. **农场推进**：每一局（无论胜负）都算一次生长
6. 被动产出入账：`maturePlots × yieldPerPlot`

## 9. 技术架构（这是交付质量的关键）

### 9.1 文件职责

| 文件 | 职责 | 行数级 |
|---|---|---|
| `game/config.js` | **所有数值**（价格、概率、时长、上限） | ~870 |
| `game/logic.js` | **纯模拟**，不许有 DOM / Phaser / storage | ~2200 |
| `game/hub.js` | 基地规则、点位、面板动作（`zoneActions` / `perform`） | ~466 |
| `game/profile.js` | 存档序列化 / 迁移 / 导出码 | ~126 |
| `game/sprites.js` | 纹理 → dataURL、按内容紧裁切 `fitUrl` | ~190 |
| `game/baghud.js` | 背包 DOM 浮层 | ~1100 |
| `game/audio.js` | WebAudio 合成器（**自建 AudioContext**，不是 Phaser 的） | ~314 |
| `game/app.js` | Phaser 表现层（Boot / Hub / Run / Farm 四个场景） | ~3200 |
| `game/index.html` | DOM 覆盖层：面板、背包、ESC 菜单、toast | ~1300 |
| `game/bosspose.js` | Boss 姿态计算（六节手臂 + 呼吸 + 步态） | ~10K |

**渲染器是 CANVAS**（`Phaser v3.80.1 (Canvas | Web Audio)`），不是 WebGL。
**所有美术除 6 张 Boss PNG 外都是 `Graphics.generateTexture` 烘出来的**——所以部署不会 404，也没有一堆占位图。

### 9.2 逻辑与渲染彻底分离（这是能让 CI 测 Canvas 游戏的原因）

Canvas 游戏很容易被判「MVP 无法自动验证」。解法：

```
game/logic.js   纯状态机，不碰 DOM/Canvas → Node 里能直接跑
game/app.js     只负责画，不改状态
```

**`logic.js` 可测的东西**：波次推进、清波/死亡判定、战利品结算、**作物成熟计时**、强化生效后数值、存档序列化/反序列化、**固定随机种子的确定性**（同种子同结果）。

> **架构上刻意划的边界**：引擎只管画、收键、放特效；**规则仍在纯逻辑层**。
> 这样 1567 项测试验证的就是**玩家实际玩的那套规则**，不会出现「测的和玩的是两套」。

## 10. 那些只有「看图」才能发现的 bug（重要教训）

这个项目反复验证了一条：**逻辑测试全绿，画面照样可以是错的。**

用 Electron 无头窗口截图后，抓到一批测试根本发现不了的 bug：

| Bug | 现象 | 根因 |
|---|---|---|
| **Graphics 累积** | 战斗画面右上一条红黑长条 | Phaser `Graphics` **会累积绘制命令**，每帧画血条却忘了 `clear()`，几百帧叠成糊 |
| **敌人纹理串了** | 吐酸虫画成了爬虫 | 精灵池**按索引复用**，纹理在创建时固定；索引 0 从爬虫换成吐酸虫时纹理没跟着换 |
| **敌人会隐形但还能打你** | 只剩一条血条挂在空中 | 同一索引复用 + 死亡循环把 alpha 压到 3%，后面敌人往上顶一格**继承了透明度** |
| **掉落物从来没被画出来过** | 逻辑、测试全对，玩家看不到 | `grep pickup game/app.js` **零命中**——测试验证了浏览器没实现的东西 |
| **树长在田里** | 田块之间冒出松树 | 背景树林按原位置绘制，正好落在新增的耕地范围上 |
| **麦穗像黄色箭头** | 作物是三角形 | 纹理是矩形+两个三角，缩小后读作箭头 |

另外两个「测试通过但功能是坏的」案例：

- **W/S 方向反了**，但测试**把 bug 当成正确行为写进去了**（断言的是「按 S 让 z 变大」，而屏幕上反了）。改成断言**屏幕坐标**才抓到。
- **结算卡可以关成一个死界面**：✕ 的处理函数是空的，关掉后 HUD 已关、战场冻结、没有出口，只能刷新。

## 13. 如果要 3D 化（给接手的 agent 的技术提示）

⚠️ **注意**：上文 §2.2 提到的作业评分约束（"visual polish alone earn no marks"）——**3D 化在评分表上可能加 0 分**，且会吃掉全部缓冲时间。但如果目标是「做一个 3D 版」而不是「交这份作业」，以下是技术事实：

### 13.1 好消息：逻辑层本来就是 3D 的

`logic.js` 里一直是 `(x, z, h)` 三轴——x 水平、z 纵深、h 高度，**36 处引用**。

**这意味着**：规则、测试（1567 项断言）、平衡、存档、五个技能、三种敌人、Boss 全部**不用改**。要重写的只有 `app.js` 这层渲染（约 3200 行）。

> 这个改动比「把 2D 游戏改成 3D」便宜得多。

### 13.2 需要重点处理的渲染层问题

| 现有 2D 做法 | 3D 里要改成 |
|---|---|
| `z` 映射为屏幕 y 偏移（`Z_TO_Y`，值 1.02） | 真透视相机 + 真实世界坐标 |
| 深度 = 屏幕 y 排序 | 真 Z-buffer |
| 程序生成 2D 纹理 | 3D 模型 / 或保持 billboard |
| `GROUND_Y = 515` 地面基线 | 真实地面平面 |

### 13.3 关键设计属性必须保住

以下三条是**设计成立与否的关键**，3D 化时**不能丢**：

1. **命中判定必须同时用 `(x, z)` 两轴**（`ATTACK_DEPTH = 55`）——否则深度轴退化
2. **吐酸虫弹道只覆盖一条深度线**（`projDepth = 26`）——否则「换深度躲避」失效
3. **三段普攻射程 ≥ Boss 贴身间距**（`hitRadius 74 - bodyRadius 46` 的分离）——否则又回到「贴脸才能打到」

建议把这三条写成 3D 版的回归测试。

### 13.4 技术选型参考

- `three.js` 0.160 可以本地 vendor（**670 KB**），离线和 GitHub Pages 都没问题
- 现有 Phaser 3.80.1 也是本地 vendor（1.1 MB），这个模式可以照搬
- ⚠️ 现在所有美术是程序生成的 2D 贴图；**3D 里会变成方块和胶囊，除非再做模型，否则比现在更难看**

## 附录 B：关键数值的「为什么」

改任何数值前先看这一节，否则会破坏设计意图：

| 数值 | 为什么是这个值 |
|---|---|
| `WAVE_HEAL = 18` | 没有回血时长局数学上不可能通关 |
| `FORGE.lootMul = 3.5` | 经济张力的来源：高风险必须对应高回报 |
| `UPGRADES` 幅度约 2× | 3× 会让中期强化通杀四档，经营吃掉核心张力 |
| 装备价格挤在 680–900 | 让玩家按打法选，不是按数值选 |
| 装备强度 ≤ 1.3× | 防止唯一最优解 |
| `plotPrice = 3000` | 334 局回本，是长线目标不是小道具 |
| `seedSpoilRate = 0.25` | 囤种子无上限且无用途，必须让它衰减 |
| 药水「每局重买」 | 唯一永不枯竭的铜币出口 |
| `armWidth 10/4` | 7/2.5 落屏太细，1x 下读不出手臂 |
| `armColor 0x7a6a55` | 本体 0x4a4038 太深，同色系看不见 |
| `wither.windup = 1.40` | 必须 > 反应 + 按键时间(0.35s)，闪现是唯一解法 |
| Boss 两个半径分离 | 共用一个会让「调大更好打中」变成「推得更远更难打」 |
| 震地靠硬直而非冲量 | 只加倍冲量实测只推开 19px（每帧走位吃掉） |
| 冲刺无惯性 | 有滑行就没法精确停在攻击距离上 |
| 深度倍率 1.27 < 水平 1.62 | 前后也 1.62 会让瞄准变滑，躲弹道更难 |
